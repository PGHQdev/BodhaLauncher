# Onboarding: five steps, one grant, no permissions step

Onboarding is **promise, essentials, friction, first intention, become home** — five steps, and the only thing it asks for is the home role.

**There is no permissions step.** Spec #16's step 4 explained each optional permission and opened the system screen; spec #18's user stories 13–16 say the opposite one capability at a time — usage access only at first touch of screen-time context, notification access only on first opening the inbox, contacts only on first contact search, calendar only when next-event surfaces are first enabled. #18 handed the sequencing to #16, so the conflict resolves here, in #18's favour: onboarding requests nothing optional and every capability is earned at the feature that needs it, through the education screens that already exist. Front-loading the grants was rejected because it asks for the most sensitive one — notification access — before the user has seen the inbox, and makes it the price of finishing setup.

The accepted cost is the one ADR 0017 named: a new user swiping right meets a Today with three named turn-on states. The promise step carries **one sentence** about it — Bodha asks for nothing until a feature needs it, and nothing leaves the phone — which is the honest residue of the dropped step. That single line makes the turn-on states read as the design working rather than as setup left unfinished, and states ADR 0009's position once, at the only moment the whole audience is present. A dedicated privacy screen was rejected as a sixth screen making a claim the user cannot yet evaluate.

**The home-role request is step five**, not a trailing handoff, so "maximum five steps" describes the whole flow rather than five steps plus a sixth thing. It comes last because the state written in steps two to four is what the user sees the moment they press Home. Asking first was rejected: it is the largest ask an unknown app can make, arriving before the user has seen anything Bodha does.

**Declining the role is an answer.** Onboarding completes either way and keeps everything configured. Without the role Bodha runs as an app you open: Home renders, Open Check still fires on launches made from Bodha, but nothing meets the user at unlock. Home carries one factual line naming that state, and Settings holds the row that re-opens the request — the only way back. There is no automatic re-prompt, matching #18's treatment of a "no". `RoleManager.isRoleHeld(ROLE_HOME)` is checked on resume, so a user who switches launchers later lands in the same named state rather than a surprise. A hard gate was rejected because it strands everything configured in the four steps before it, on the one screen users most often back out of.

**Essentials** writes `PinStore`. With usage access no longer requested here, there is no data to rank by, so the picker lists launchable apps alphabetically from `AppCatalog`. The copy suggests four to eight and gates nothing — no minimum, no maximum, continue always enabled. Skipping writes no pins and Home starts empty with its own state, inviting the first pin and pointing at the App Library. Seeding defaults from role holders was rejected: it is Bodha deciding what matters to someone who declined to say, and ADR 0016 has already refused to ship anything pre-made.

**Friction** writes `OpenCheckRuleStore`, capped at three apps, each `OpenCheckRule(OpenCheckMode.Always)` — the one mode explainable in a sentence to someone who has not met the feature; the other four are configuration, reached later from an app's long-press. The three is stated as a plain fact ("three to start, change any of it later") and **Pro is not named**, because ADR 0005 caps free Open Check at three and an unbounded picker would put a paywall in step three of onboarding, which spec #16's own rules forbid. Skipping writes nothing and no app is checked.

**Pro is absent from onboarding entirely** — no screen, no copy, no upsell. The first mention is the existing `GateDecision` text at a wall the user walked into: a fourth Open Check rule, Awareness past seven days, Focus scheduling, Reflection. A Settings row is the only other place. This is ADR 0005's resentment-moment reasoning applied to the first ten minutes.

**Each step commits to its real store on advance** — no draft layer, since the stores are the only place the state can live. A completion flag is written when step five resolves either way, granted or declined, and onboarding never appears again. Interrupted, the next launch resumes at the first step not passed and keeps everything already written. There is **no re-run**: all four configured things are ordinary surfaces afterwards, so a re-run could only overwrite deliberate choices. Inferring completion from an empty `PinStore` was rejected — Q4 makes an empty Home a legitimate outcome, and it would re-run forever.

Onboarding is **explicitly exempt from ADR 0011**. It is a flow, not a surface: no swipe reaches it, Search does not resolve it, it is absent from the glossary's surface list. Back steps to the previous step and back on step one leaves the app; the radial model begins the moment the completion flag is set. The exemption is stated rather than left implicit so the contradiction with "back always returns Home" is not later found and "fixed".

Resolved in issue #96.
